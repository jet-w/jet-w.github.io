Pod设计理念

什么是Pod

Pod是Kubernetes中最小的可部署单元，一个Pod代表集群中运行的一个进程。Pod封装了一个或多个容器、存储资源、网络IP以及控制容器运行的选项。

Pod的核心特性
  • 共享网络：同一Pod内的容器共享IP和端口空间，可通过localhost互相访问
  • 共享存储：容器可以挂载相同的Volume，实现数据共享
  • 共享命名空间：可选共享PID、IPC等命名空间
  • 原子调度：Pod中的所有容器总是被调度到同一节点

Pod解决的问题：

场景单容器Pod多容器
紧耦合应用需要网络配置localhost直接通信
共享存储需要额外配置天然共享Volume
协同调度可能分散保证同节点
生命周期独立管理统一管理

Pod生命周期

生命周期阶段

🔄 正在渲染 Mermaid 图表...
stateDiagram-v2
    [*] --> Pending: 创建Pod
    Pending --> Running: 所有容器启动
    Pending --> Failed: 启动失败

    Running --> Succeeded: 正常完成(Job)
    Running --> Failed: 容器异常退出
    Running --> Unknown: 节点失联

    Failed --> [*]: 清理
    Succeeded --> [*]: 清理
    Unknown --> Running: 节点恢复
    Unknown --> Failed: 节点确认失效

Pod状态详解

状态含义常见原因
PendingPod已创建但未运行镜像拉取中、资源不足、调度中
RunningPod已绑定节点，容器已创建至少一个容器在运行
Succeeded所有容器成功终止Job类型Pod正常完成
Failed所有容器终止，至少一个失败容器退出码非零
Unknown无法获取Pod状态节点通信异常

重启策略

apiVersion: v1
kind: Pod
metadata:
  name: restart-demo
spec:
  restartPolicy: Always  # Always | OnFailure | Never
  containers:
  - name: app
    image: nginx
策略行为适用场景
Always容器退出后总是重启长期运行的服务
OnFailure仅失败时重启批处理任务
Never从不重启一次性任务

Pod配置详解

完整的Pod规范

apiVersion: v1
kind: Pod
metadata:
  name: complete-pod-example
  namespace: default
  labels:
    app: myapp
    version: v1
  annotations:
    description: "完整Pod示例"
spec:
  # 容器定义
  containers:
  - name: main-container
    image: nginx:1.24
    imagePullPolicy: IfNotPresent  # Always | Never | IfNotPresent

    # 端口配置
    ports:
    - name: http
      containerPort: 80
      protocol: TCP

    # 环境变量
    env:
    - name: ENV_VAR
      value: "production"
    - name: POD_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.name
    - name: SECRET_KEY
      valueFrom:
        secretKeyRef:
          name: my-secret
          key: password

    # 资源限制
    resources:
      requests:
        memory: "128Mi"
        cpu: "100m"
      limits:
        memory: "256Mi"
        cpu: "500m"

    # 存储卷挂载
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
    - name: data-volume
      mountPath: /data

    # 健康检查
    livenessProbe:
      httpGet:
        path: /healthz
        port: 80
      initialDelaySeconds: 15
      periodSeconds: 10

    readinessProbe:
      httpGet:
        path: /ready
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 5

    startupProbe:
      httpGet:
        path: /startup
        port: 80
      failureThreshold: 30
      periodSeconds: 10

  # Init容器
  initContainers:
  - name: init-db
    image: busybox
    command: ['sh', '-c', 'until nc -z db-service 3306; do sleep 2; done']

  # 存储卷定义
  volumes:
  - name: config-volume
    configMap:
      name: app-config
  - name: data-volume
    emptyDir: {}

  # 调度配置
  nodeSelector:
    disktype: ssd
  tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"

  # 服务账号
  serviceAccountName: default

  # DNS策略
  dnsPolicy: ClusterFirst

  # 重启策略
  restartPolicy: Always

  # 终止宽限期
  terminationGracePeriodSeconds: 30

健康检查

三种探针类型

🔄 正在渲染 Mermaid 图表...
flowchart LR
    subgraph Probes[探针类型]
        L[livenessProbe<br/>存活探针]
        R[readinessProbe<br/>就绪探针]
        S[startupProbe<br/>启动探针]
    end

    L -->|失败| RESTART[重启容器]
    R -->|失败| REMOVE[从Service移除]
    S -->|失败| KILL[杀死容器]
    S -->|成功| ENABLE[启用其他探针]

    style L fill:#ffcdd2
    style R fill:#fff9c4
    style S fill:#c8e6c9

作用： 检测容器是否存活，失败则重启容器

livenessProbe:
  # HTTP探测
  httpGet:
    path: /healthz
    port: 8080
    httpHeaders:
    - name: Custom-Header
      value: Awesome
  initialDelaySeconds: 15  # 首次探测延迟
  periodSeconds: 10        # 探测间隔
  timeoutSeconds: 3        # 超时时间
  successThreshold: 1      # 成功阈值
  failureThreshold: 3      # 失败阈值

适用场景： 检测应用死锁、无响应等情况

作用： 检测容器是否准备好接收流量

readinessProbe:
  # TCP探测
  tcpSocket:
    port: 3306
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3

适用场景： 应用启动需要加载数据、预热缓存等

作用： 检测容器内应用是否已启动

startupProbe:
  # 执行命令探测
  exec:
    command:
    - cat
    - /tmp/healthy
  failureThreshold: 30     # 最多尝试30次
  periodSeconds: 10        # 最长等待300秒

适用场景： 启动时间长的遗留应用

探测方式对比

# 方式1: HTTP GET探测
httpGet:
  path: /healthz
  port: 8080
  scheme: HTTP  # 或 HTTPS

# 方式2: TCP Socket探测
tcpSocket:
  port: 3306

# 方式3: 执行命令探测
exec:
  command:
  - sh
  - -c
  - test -f /app/ready

# 方式4: gRPC探测 (K8s 1.24+)
grpc:
  port: 50051
  service: my.health.v1.Health

Sidecar模式示例

# 日志收集Sidecar
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-logging
spec:
  containers:
  # 主应用容器
  - name: app
    image: busybox
    command: ['sh', '-c', 'while true; do echo "$(date) INFO: App running" >> /var/log/app.log; sleep 5; done']
    volumeMounts:
    - name: log-volume
      mountPath: /var/log

  # Sidecar日志收集容器
  - name: log-collector
    image: busybox
    command: ['sh', '-c', 'tail -f /var/log/app.log']
    volumeMounts:
    - name: log-volume
      mountPath: /var/log

  volumes:
  - name: log-volume
    emptyDir: {}

      value: "3306"

  # Ambassador代理容器
  - name: db-proxy
    image: mysql-proxy:1.0
    env:
    - name: MYSQL_HOST
      value: "mysql-primary.database.svc.cluster.local"
    - name: MYSQL_REPLICA
      value: "mysql-replica.database.svc.cluster.local"
    ports:
    - containerPort: 3306

Init容器

Init容器特点

🔄 正在渲染 Mermaid 图表...
sequenceDiagram
    participant K as Kubernetes
    participant I1 as Init Container 1
    participant I2 as Init Container 2
    participant A as App Container

    K->>I1: 启动Init容器1
    I1-->>K: 完成
    K->>I2: 启动Init容器2
    I2-->>K: 完成
    K->>A: 启动应用容器

    Note over I1,I2: Init容器按顺序执行<br/>必须全部成功才会启动应用容器
Init容器的特点
  • 总是运行到完成
  • 按定义顺序依次执行
  • 任一Init容器失败，Pod会重启
  • 完成后才会启动主容器
  • 不支持探针（因为必须运行到完成）

Init容器使用场景

apiVersion: v1
kind: Pod
metadata:
  name: init-demo
spec:
  initContainers:
  # 场景1: 等待依赖服务就绪
  - name: wait-for-db
    image: busybox
    command: ['sh', '-c', 'until nc -z mysql-service 3306; do echo waiting for mysql; sleep 2; done']

  # 场景2: 下载配置文件
  - name: download-config
    image: curlimages/curl
    command: ['sh', '-c', 'curl -o /config/app.conf http://config-server/app.conf']
    volumeMounts:
    - name: config
      mountPath: /config

  # 场景3: 修改系统参数
  - name: sysctl
    image: busybox
    command: ['sh', '-c', 'sysctl -w net.core.somaxconn=65535']
    securityContext:
      privileged: true

  # 场景4: 数据库迁移
  - name: migrate
    image: myapp:1.0
    command: ['./migrate', '--database', '$(DATABASE_URL)']
    env:
    - name: DATABASE_URL
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: url

  containers:
  - name: app
    image: myapp:1.0
    volumeMounts:
    - name: config
      mountPath: /config

  volumes:
  - name: config
    emptyDir: {}

Pod状态排查

flowchart TD
    START[Pod异常] --> CHECK{检查状态}

    CHECK --> |Pending| P[Pending状态]
    CHECK --> |CrashLoop| C[CrashLoopBackOff]

    P --> P1{资源不足?}

    P2 --> P2S[检查nodeSelector/affinity]

    C --> C1[查看日志<br/>kubectl logs --previous]
    C1 --> C2[检查启动命令和探针]

    I --> I1{镜像存在?}
    I1 --> |否| I1S[检查镜像名称和标签]
    I1 --> |是| I2{认证问题?}
    I2 --> I2S[配置imagePullSecrets]

    O --> O1[增加内存limits]
    O1 --> O2[优化应用内存使用]

常见错误
  • CrashLoopBackOff: 检查启动命令、环境变量、健康检查配置
  • ImagePullBackOff: 检查镜像名称、标签、仓库认证
  • OOMKilled: 增加内存限制或优化应用内存使用
  • CreateContainerError: 检查安全上下文、存储卷配置
